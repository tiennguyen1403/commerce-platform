# Research — M1 Commerce slice

> Produced at milestone start by the `researcher` agent. Read before building.

## Context & goal

M1 turns the Phase-0 scaffold into a demoable store: admin CRUD for catalog, a public storefront (SSR/ISR, SEO) reading the seeded `demo` tenant, guest cart + Stripe **test-mode** checkout, an `Order` that reaches `PAID` via the **webhook** (not the client redirect) with price-snapshotted line items, a Resend confirmation email, and an auth-protected `/admin`. Full scope/exit criteria: `docs/milestones/M1-commerce-slice/GOAL.md`.

## Key questions

1. What's Next 16's actual rendering/caching model for Prisma-backed pages (not `fetch`), and how do Server Actions, route handlers, and `generateMetadata` work now?
2. How do we auth-protect `/admin` given Better Auth's Prisma adapter isn't edge-safe?
3. PaymentIntent+Elements or Checkout Session (**Open Decision A**) — and how do we wire creation, webhook, idempotency?
4. What Prisma 6 patterns do we need for atomic Order+OrderItems creation and race-free order numbers?
5. Cookie cart or DB `Cart` model (**Open Decision B**)?
6. How/where does the Resend email fit so it survives a closed tab and never breaks the webhook?
7. How do we add shadcn primitives on top of `@base-ui/react` (not Radix), and is `globals.css` ready?

## Findings

### Framework / APIs (Next 16.3.3)

**Cache Components is OFF — the "previous model" governs this app.** `next.config.ts:3` has no `cacheComponents: true`. Per `node_modules/next/dist/docs/01-app/01-getting-started/08-caching.md:14`, without that flag you're on the "Caching and Revalidating (Previous Model)" guide (`.../02-guides/caching-without-cache-components.md`), **not** `"use cache"`/`cacheLife`/`cacheTag`/PPR. Don't reach for those APIs unless the flag is flipped (bigger, riskier change — see Risks).

- Default rendering: a route is prerendered at build **unless** it uses a Request-time API (`cookies()`, `headers()`, read `searchParams`) or sets `export const dynamic`/`revalidate`. Prisma calls are not `fetch`, so they don't auto-opt a route into dynamic rendering — the route segment config does that (`.../02-guides/caching-without-cache-components.md:82-181`).
- Dynamic segments with **no `generateStaticParams`** default to on-demand rendering (`dynamicParams` defaults `true` — `.../03-file-conventions/02-route-segment-config/dynamicParams.md:16`). So a PDP at `/products/[slug]` is SSR "for free," no config needed.
- `cookies()`, `headers()`, `params`, `searchParams` are all **async** — `await` them (`.../04-functions/cookies.md:67`; `.../03-file-conventions/page.md:64`).
- **`middleware.ts` is deprecated, renamed `proxy.ts`** (`.../03-file-conventions/proxy.md:11`, version history at `:802-813`). No `middleware.ts`/`proxy.ts` exists in the repo yet. Proxy defaults to the **Node.js runtime** now (not edge) — `.../03-file-conventions/proxy.md:253-255,806`. This is a real behavior change vs. pre-16 Next/training data.
- Route handlers: raw body via `await request.text()`, signature header via `request.headers.get('stripe-signature')` on the raw `Request` — matches the doc's own "Webhooks" example (`.../03-file-conventions/route.md:559-595`). Route Handlers default to Node runtime already; just don't set `export const runtime = 'edge'`.
- `generateMetadata({params})` — `params` is a `Promise`, `await` it (`.../04-functions/generate-metadata.md:50-79`).
- `revalidateTag(tag, profile)` **now requires the 2nd argument** (e.g. `'max'`); the 1-arg form is deprecated even outside Cache Components (`.../04-functions/revalidateTag.md:35,61`).

**Repo convention: don't use generated `PageProps`/`LayoutProps`/`RouteContext` types.** Commit `3279af1` replaced `LayoutProps<"/">` with explicit `Readonly<{children: ReactNode}>` in `src/app/layout.tsx:22-24` because `.github/workflows/ci.yml:24-27` runs `lint → typecheck → build` — `tsc --noEmit` runs **before** `next build`/`next typegen` ever generates `.next/types/**` (which `tsconfig.json:29-30` includes), so the global helper types don't exist yet on a clean checkout and typecheck fails. **Apply the same pattern to every new M1 route** (PDP `[slug]`, admin `[id]` edit pages, route handlers): explicit `{ params }: { params: Promise<{ slug: string }> }`, not `PageProps<'/products/[slug]'>`.

**Concrete, verified CI risk: `pnpm build` will likely break once a storefront page does a plain Prisma read.** `.github/workflows/ci.yml:12` sets `DATABASE_URL=postgresql://postgres:postgres@localhost:5432/dropshipping` but the workflow has **no Postgres service** — nothing listens on `5432` in CI (also note: local dev uses port **55432**, a second mismatch). A product-listing page with no dynamic segment and an unguarded `await prisma.product.findMany(...)` will be statically prerendered at `next build` time and will try (and fail) to reach that DB. The PDP is safe (renders on-demand, see above); **the index/listing page is the one at risk.**

### Libraries / services

**Stripe (`stripe` 22.6.0).** `src/lib/stripe.ts:16` calls `new Stripe(key)` with no `apiVersion` — the SDK auto-pins `'2026-08-26.dahlia'` (`node_modules/stripe/cjs/apiVersion.js:5`), so current code is already correct; passing it explicitly is just insurance against silent drift on a future `stripe` bump.

- Webhook verify: `stripe.webhooks.constructEvent(rawBody, sig, secret)` — sync, fine on Node runtime (route handlers default Node); use `constructEventAsync` only if ever moved to edge (`node_modules/stripe/cjs/Webhooks.js:17-33`).
- `@stripe/react-stripe-js` current published version **6.8.2**, `@stripe/stripe-js` **9.14.0** (verified via raw GitHub `package.json`) — neither is installed yet.

**Better Auth (1.7.2) + Prisma adapter.**

- `getSession` endpoint confirmed: returns `{session, user}`, `requireHeaders: true` (`node_modules/better-auth/dist/api/index.d.mts:238-269`). `getSessionCookie(request): string|null` confirmed exported from `better-auth/cookies`, no DB hit (`node_modules/better-auth/dist/cookies/index.d.mts:104-108`).
- **Recommended split** (matches Next's own auth guide, `.../02-guides/authentication.md:1026-1127`): `proxy.ts` does an **optimistic** `getSessionCookie()` check only (redirect if absent) — Proxy is Node-runtime now, but Next's docs still warn against DB checks there ("avoid database checks to prevent performance issues," runs on every request incl. prefetches). The admin layout (Server Component) does the **authoritative** check: `await auth.api.getSession({ headers: await headers() })`, then resolves `Membership` → `hasAtLeast(role, 'STAFF')` (`src/config/roles.ts:17`).
- **Non-obvious gotcha for seeding**: Better Auth stores the password hash on `Account` (`providerId: "credential"`, confirmed at `node_modules/better-auth/dist/api/routes/sign-up.mjs:245-246`), **not** on `User` (`prisma/schema.prisma:56-68` has no password field; `Account.password` at `:96` does). `prisma/seed.ts` cannot do a plain `prisma.user.create()` with a password — it must call `auth.api.signUpEmail({ body: { name, email, password } })` (confirmed shape: returns `{ token, user: { id, ... } }`, `node_modules/better-auth/dist/api/index.d.mts:343-373`), then create the `Membership` row. Skipping this produces a `User` that can never sign in.

**Prisma 6.19.3.**

- Interactive transactions confirmed: `$transaction<R>(fn: (tx) => Promise<R>, {maxWait?, timeout?, isolationLevel?})` (`node_modules/@prisma/client/runtime/library.d.ts:897-901`).
- `@@unique([tenantId, orderNumber])` (`prisma/schema.prisma:187`) — avoid SELECT-MAX-then-increment (races). Generate a non-sequential candidate (date prefix + short random suffix), catch `PrismaClientKnownRequestError` with `code === 'P2002'` (confirmed exported, `.../library.d.ts:2626-2633`) and retry (bounded).

**Resend** (not installed, add `resend` ^6.25 — verified via raw GitHub `package.json`, version `6.25.0`). `@react-email/render` is only an _optional_ peer — `html: '<p>...</p>'` works standalone, no `@react-email/components` needed for M1. Send **from the webhook**, after the `PAID` transition, wrapped so a send failure can't turn the webhook's response into non-2xx (log + swallow).

**zod 4.5.4** confirmed installed. Custom-message key is now `{ error: '...' }`, not `{ message: '...' }` (old key still works but deprecated — seen in Next's own docs example at `.../02-guides/authentication.md:113-124`). Prefer the new spelling in new schemas.

**`@base-ui/react` 1.7.0 + shadcn `"style": "base-nova"` (`components.json:3`).** Confirmed export map (`node_modules/@base-ui/react/package.json:61-1210`) includes `./dialog`, `./select`, `./field`, `./fieldset`, `./form`, `./input`, `./toast`, `./checkbox`, `./separator`, `./tabs` — **no `./card`, `./badge`, `./table`, standalone `./label`** (these are plain styled markup in every shadcn style, base or Radix, so that's expected, not a gap). Base UI ships its **own `./toast`** — the M1 primitive list mentions "sonner," but under `base-nova` the generated toast almost certainly wraps `@base-ui/react/toast`; **don't add `sonner`** until you've confirmed the CLI output needs it. `src/app/globals.css:50-117` already has the full OKLCH token set light+dark — setup is done, don't recreate it.

### Patterns to follow

**Open Decision A — Stripe: recommend raw PaymentIntent + Elements/PaymentElement, not Checkout Sessions.**

- In-repo evidence all points one way: `docs/ARCHITECTURE.md:57` — "Payment via **Stripe** (Payment Intents)"; `GOAL.md:14` — "Stripe **Payment Intent**"; `prisma/schema.prisma:180` — `stripePaymentIntentId String? @unique` (not a session-id field). The data model already assumes we own the Order/line-items and just attach a PaymentIntent.
- Countervailing signal to flag honestly: Stripe's **live** docs now steer new integrations to Checkout Sessions with `ui_mode:"elements"` ("Stripe recommends using the Checkout Sessions API with the Payment Element over Payment Intents for most integrations... requires significantly more code" — fetched from `docs.stripe.com/payments/quickstart`). `@stripe/react-stripe-js`'s own README concedes the classic flow is still fully supported, just framed as "more fine-grained control, but requires significantly more code and ongoing maintenance." Given the three pieces of in-repo evidence above plus the explicit portfolio-value framing (a hand-built PaymentIntent flow is a more legible "I built this" artifact than dropping in Stripe's hosted line-item/tax engine), **stay with the classic flow.**
- Flow: create PaymentIntent server-side first (`stripe.paymentIntents.create({amount: totalCents, currency, metadata: {orderId, tenantId}})`) → in the same `$transaction`, create Order (`PENDING`, `stripePaymentIntentId` already set) + OrderItems (snapshot `titleSnapshot`/`priceCents` from a **fresh** DB read of the variants, never client input) → return `client_secret` to the client, which renders `<Elements stripe={loadStripe(NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY)} options={{clientSecret}}><PaymentElement/></Elements>` and confirms via `useStripe()`/`useElements()` + `stripe.confirmPayment(...)`.
- Webhook (`payment_intent.succeeded`): find Order by `stripePaymentIntentId` (unique lookup already in schema) → **idempotency = order-status guard**: no-op if `order.status !== 'PENDING'`. This is sufficient for M1 (handles Stripe's automatic retries with zero new schema) and matches Stripe's own guidance to dedupe by the object id + event type rather than `created` timestamps (event ordering isn't guaranteed). A `WebhookEvent` log table is a fine M2 hardening item, not needed now.
- Local dev: `stripe listen --forward-to localhost:3000/api/webhooks/stripe`, copy the printed `whsec_...` into `STRIPE_WEBHOOK_SECRET`.

**Open Decision B — Cart: recommend cookie-backed, not a DB `Cart` model.**

- No `Cart` model exists; GOAL frames this as guest checkout on one seeded tenant. Store `[{variantId, qty}]` — **never price** — as JSON in a cookie (`httpOnly: true, sameSite: 'lax', secure` in prod), mutated by Server Actions (`addToCart`/`updateQty`/`removeFromCart`). Cart display **and** checkout always re-read the `ProductVariant` rows fresh from Prisma for current `priceCents`/`stock`/title — cookie tampering can at most select an invalid `variantId` or an oversized `qty`, both caught by that same re-validation. Zero migration risk for M1; a DB `Cart` becomes worth it once there's cross-device/logged-in persistence to design for (M2+), and the "always recompute at checkout" contract carries over unchanged.

**Tenant resolution for M1** (no subdomains yet, that's M3): storefront reads a hardcoded `DEMO_TENANT_SLUG` constant (e.g. `src/config/constants.ts`) → `tenantRepository.findBySlug(...)`; admin resolves tenant from the signed-in user's `Membership`, never from a param.

**New repository methods needed** (all tenant-scoped, following `src/server/repositories/product.repository.ts`'s pattern): `tenantRepository.findBySlug`; `productRepository.listAllByTenant` (incl. drafts), `.update`, `.archive`, variant `create`/`update`/`delete`; `orderRepository.createWithItems`, `.findByPaymentIntentId`, `.markPaidByPaymentIntent`; `membershipRepository.findForUser`.

**Env additions**: make `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` required (currently `.optional()` in `src/lib/env.ts:10-11` — fine when Stripe was N/A, not fine now that M1 depends on them); add `RESEND_API_KEY` (server-only, same schema). Add `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` to `.env.example` only — it must be referenced as a literal `process.env.NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` at the exact call site for Next's build-time inlining to work (`node_modules/next/dist/docs/01-app/02-guides/environment-variables.md:182-192`), and it must **not** go through `src/lib/env.ts` (that file is `server-only`, `src/lib/env.ts:1`).

**Suggested route layout** (non-binding — avoids disturbing the existing marketing `/`):

```
src/app/(storefront)/products/page.tsx           # list — needs export const dynamic = 'force-dynamic' (see risk)
src/app/(storefront)/products/[slug]/page.tsx    # PDP + generateMetadata — SSR by default, no config needed
src/app/(storefront)/cart/page.tsx
src/app/(storefront)/checkout/page.tsx           # <Elements> + <PaymentElement>
src/app/(storefront)/checkout/success/page.tsx
src/app/api/checkout/route.ts                    # create PaymentIntent + PENDING Order (or a Server Action)
src/app/api/webhooks/stripe/route.ts             # raw body, constructEvent, PENDING→PAID, email
src/app/(admin)/admin/layout.tsx                 # auth.api.getSession + Membership gate
src/app/(admin)/admin/products/**                # CRUD
proxy.ts                                         # repo root, next to src/ — optimistic cookie check
```

## Risks & unknowns

| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **CI has no Postgres service**, but a storefront index page with a plain Prisma read will be prerendered at `next build` → CI build breaks                                  | `export const dynamic = 'force-dynamic'` on that page for M1 (satisfies GOAL's "SSR" language, zero CI risk); add a Postgres service + `revalidate`-based ISR as a fast-follow if wanted                                                                                   |
| Using `middleware.ts` out of habit — **Next 16 renamed it to `proxy.ts`**                                                                                                   | Create `proxy.ts` at the repo root; don't rely on training data here                                                                                                                                                                                                       |
| `PageProps`/`LayoutProps`/`RouteContext` generated types don't exist when `tsc --noEmit` runs in CI                                                                         | Follow the repo's own established convention (commit `3279af1`) — explicit inline Promise types on every new route                                                                                                                                                         |
| Webhook idempotency & event ordering                                                                                                                                        | Order-status guard (`PENDING` → no-op if already `PAID`); don't rely on `event.created`/timestamps for ordering (Stripe doesn't guarantee it)                                                                                                                              |
| Trusting client-sent prices                                                                                                                                                 | Never store/accept price from cart cookie or client; always recompute `priceCents`/`totalCents` from `ProductVariant` at PaymentIntent-creation time                                                                                                                       |
| Tenant scoping on new repo methods                                                                                                                                          | Every new method takes `tenantId` as an explicit first-class arg, mirrors `product.repository.ts`'s existing shape                                                                                                                                                         |
| `server-only` leakage into client bundle                                                                                                                                    | `getStripe()`/repos/`env.ts` already guarded by `import "server-only"` — keep new server modules the same way; the one exception is `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, which is _meant_ to reach the client and must bypass `env.ts` entirely                           |
| Order-number races under concurrent checkout                                                                                                                                | Non-sequential candidate (date + random) generated inside the `$transaction`; catch Prisma `P2002` and retry, bounded                                                                                                                                                      |
| Email failure must not fail the webhook                                                                                                                                     | `try/catch` around `resend.emails.send(...)`, log and continue; webhook still returns 200                                                                                                                                                                                  |
| Env keys currently `.optional()` become load-bearing                                                                                                                        | Flip `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` to required in `src/lib/env.ts`, add `RESEND_API_KEY`                                                                                                                                                                     |
| Stripe `apiVersion` mismatch on future SDK bumps                                                                                                                            | SDK auto-pins `2026-08-26.dahlia` when omitted (current code is fine); optionally hardcode for reproducibility                                                                                                                                                             |
| Better Auth + edge/runtime constraints                                                                                                                                      | Proxy now defaults to Node (16.0.0+) so this is less scary than pre-16, but Next's own guidance still says keep Proxy to a cookie-only check; the Prisma-backed authoritative check belongs in the Server Component layout, which is Node by default                       |
| **Seeding an admin user isn't `prisma.user.create()`** — password lives on `Account`, not `User`                                                                            | `prisma/seed.ts` must call `auth.api.signUpEmail(...)` then create the `Membership`; otherwise `/admin` stays untestable (exit criterion blocked)                                                                                                                          |
| Base UI + shadcn `base-nova` combo is newer/less proven than the default Radix path                                                                                         | Run the CLI, actually read the generated `form`/`field` output before assuming react-hook-form-style APIs; the button primitive's existing pattern (`ButtonPrimitive` + `cva` + `cn`) is the template to match                                                             |
| `--font-sans` in `globals.css:9` self-references instead of pointing at `--font-geist-sans` (`layout.tsx:6-9`); no OKLCH accent hue defined despite DESIGN.md requiring one | Not blocking M1 functionality — fix opportunistically or fold into GOAL's "polish pass" issue                                                                                                                                                                              |
| Whether `cacheComponents: true` should be adopted for real ISR/PPR                                                                                                          | Explicitly **not recommended for M1** — bigger surface area (Suspense-everywhere, `use cache` constraints, still labeled recent/16.0.0-era) for a milestone that only needs "server-rendered with correct metadata"; revisit post-M1 if the portfolio wants to show it off |

## Recommended approach

Build in this order, matching GOAL's suggested breakdown but sequenced around the dependency chain research surfaced: **(1)** tenant/membership plumbing first — `tenantRepository`, `membershipRepository`, seed script updated to create an admin `User`+`Account` via `auth.api.signUpEmail` + `Membership`, since nothing admin-side is testable without it; **(2)** `proxy.ts` + admin layout auth gate, using the optimistic-cookie/authoritative-session split above; **(3)** admin catalog CRUD (repositories → services → Server Actions → forms), which also proves out the shadcn/Base UI primitive additions early; **(4)** storefront list+PDP, deciding `force-dynamic` vs. ISR for the listing page up front (recommend `force-dynamic` per the CI risk); **(5)** cookie cart; **(6)** checkout (PaymentIntent creation + PENDING Order in one transaction) and the webhook (idempotent PAID transition) together, since they share the Order-lookup contract; **(7)** Resend email wired into the webhook's success path; **(8)** design polish pass, including the two small `globals.css` fixes noted above. Add the env keys (`STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` required, `RESEND_API_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`) and the two new client packages (`@stripe/react-stripe-js@^6.8`, `@stripe/stripe-js@^9.14`) plus `resend@^6.25` at the start of step 6.
